# 0.2 安装、升级与回退

## 从 0.2 升级到 0.3 开发版

先在独立测试环境验证对应提交，不要将开发版直接替换生产版本。停写后，按本文方法备份数据库、应用数据目录、密钥和自定义存储目录；保存当前镜像 digest 和配置。

启动单个新版实例时，数据库按顺序从 schema 1 升级到 schema 3。schema 2 新增事项、审批记录、附件关联、通知和设置审计表，以及 Logo、时区和上传上限；schema 3 增加回收站保留期、文件用途及清理状态、重新提交来源。保留原有账号、角色、自定义菜单、设置、文件和审批记录。首次新增的上传上限默认 2048 MiB，保留期默认 30 天。旧版文件按普通文件保留，不自动关联审批或推断为未使用附件。

已使用 schema 2 的 0.3 开发版也需要升级前备份。schema 3 不会自动清理任何文件；管理员须先将未使用文件移入回收站，超过保留期后再选择永久清理。已关联审批的附件不能清理。源码构建最低需要 Go 1.24。

验收时使用两个普通账号完成提交、通知、附件下载、通过/驳回，再验证撤回、修改重提、搜索筛选、附件复用/回收/恢复、重复处理冲突及无关账号无法查看事项。确认系统设置和回收站保留期正确；永久清理仅在可丢弃的测试文件上验收。系统设置仅超级管理员可修改；工作模块对启用账号开放，数据按参与人隔离。

回退须恢复升级前的数据库与应用目录，并使用当时保存的镜像和配置。0.2 和 schema 2 开发版镜像会拒绝 schema 3 数据库；禁止只删除迁移版本记录来强行回退。运行中直接复制 SQLite 主文件可能丢失 WAL 数据，应停写并使用 SQLite backup 或 VACUUM INTO 生成一致性数据库快照，同时保存上传文件和密钥。

0.2 增加首次安装向导、独立密钥、持久化应用目录和数据库版本记录。已有数据升级会保留账号与定制菜单，但旧令牌全部失效。默认密码的超级管理员必须先改密，默认密码的普通账号将停用。

## 新安装

按 README 启动，打开 `/setup`。默认 Compose 读取安装授权码：

```bash
docker compose exec shiyu-app cat /app/data/setup-token
```

SQLite 部署：

```bash
docker compose -f docker-compose.sqlite.yml exec shiyu-app cat /app/data/setup-token
```

填写系统名称、管理员账号和 12–72 字节密码。数据库连接通过部署配置设置，向导负责检查数据库和默认存储可用性。

默认上传目录是 `/app/data/uploads`，密钥是 `/app/data/jwt.key`；整个 `/app/data` 必须持久化。SQLite 数据库在 `/data/shiyu_admin.db`，单独保留原数据库卷。自定义本地存储目录需要另行挂载。

## 从旧版本升级

以下示例在仓库根目录执行，默认使用 PostgreSQL Compose。使用其他模式时，在每个 Compose 命令中添加对应的 `-f` 参数。

### 1. 停止写入并备份

先记录当前镜像 ID、不可变标签或 digest，并保存旧 Compose 与外部配置。建议为每次备份创建独立目录。

```bash
mkdir -p backups/pre-0.2
docker inspect shiyu-app --format '{{.Image}}' > backups/pre-0.2/image-id.txt
cp docker-compose*.yml backups/pre-0.2/
docker compose stop shiyu-app
docker cp shiyu-app:/app/data backups/pre-0.2/app-data
docker compose exec -T shiyu-postgres pg_dump -U shiyu -d shiyu_admin_scaffold -Fc > backups/pre-0.2/database.dump
```

旧容器没有 `/app/data` 且从未上传过文件时，复制命令可能报目录不存在。确认实际存储配置后再继续，不要把其他错误当作空数据。自定义目录应逐个备份。备份文件中包含密钥，限制访问权限。

SQLite：停止应用后复制整个 `/data` 目录，保留可能存在的 WAL 文件：

```bash
docker compose -f docker-compose.sqlite.yml stop shiyu-app
docker cp shiyu-app:/data backups/pre-0.2/sqlite-data
```

MySQL 使用 `mysqldump`，SQL Server 使用原生 `BACKUP DATABASE`；必须先在独立环境确认备份可恢复。不要在数据库仍运行时直接打包其底层数据卷。

### 2. 准备配置和新镜像

- 使用当前版本的 Compose 文件，确认 `shiyu-app-data:/app/data` 挂载存在。
- 外部配置中的公开 `jwt.secret` 改为空，让服务创建独立密钥，或通过 `SHIYU_JWT_SECRET` 注入至少 32 字节的随机密钥。不要沿用公开示例密钥。
- 将 `SHIYU_IMAGE` 指向经过验证的固定 SHA 标签或 digest；不要把会变动的 latest 当作回退依据。
- 维持原 Compose 项目名和数据库卷名，避免误建空库。不要执行 `down --volumes`。

拉取镜像并创建尚未启动的新应用容器，将文件恢复到新的持久化卷后启动：

```bash
docker compose pull shiyu-app
docker compose create --no-deps shiyu-app
docker cp backups/pre-0.2/app-data/. shiyu-app:/app/data/
docker compose start shiyu-app
```

新安装或无旧文件时跳过复制；旧文件目录备份未确认成功时不能删除旧容器。SQLite 的数据库卷仍挂载 `/data`，不要更换或清空它。

### 3. 验证

```bash
docker compose logs --tail=100 shiyu-app
curl --fail http://localhost:18000/api/v1/system/health
```

进入系统检查“版本与升级”，确认应用版本 0.2.0、数据库版本 1，并验证管理员登录、旧成员、定制菜单、旧文件下载、新文件上传和权限隔离。完成验证再恢复业务写入。

迁移采用前向策略，完成后写入 `sys_schema_migrations`；只允许一个应用实例执行首次迁移。MySQL DDL 不具备完整事务回滚，因此失败后应保持应用停止，修复并重试，或恢复备份。

## 回退

1. 停止应用，保留当前失败现场及升级后的新增数据。
2. 恢复升级前同一时间点的数据库、应用文件、密钥和外部配置。
3. 使用升级前记录的镜像和 Compose 配置重新创建应用。
4. 验证关键功能，再恢复访问。

回退不等于只换旧镜像。本版本不执行自动删除字段或数据的 down 迁移；旧程序也未必能识别新版迁移记录。PostgreSQL 可在空的恢复数据库中使用 `pg_restore`，确认成功后切换配置。SQLite 应在应用停止时恢复备份目录。升级后的新写入不会自动出现在旧备份中，需要另行保留或接受丢弃。

## 配置与兼容边界

- `SHIYU_DATA_DIR` 指定本机数据目录；默认 `./data`，容器工作目录下为 `/app/data`。变更它不会自动迁移已有文件，需要同步目录挂载和存储配置。
- `SHIYU_JWT_SECRET` 是可选项；不设置时读取或创建 `jwt.key`，设置公开默认值或过短值将拒绝启动。
- Redis 可用于在线统计和缓存功能；会话退出以数据库记录为准，不依赖 Redis。
- 组织、角色、菜单与用户角色分配的修改仅超级管理员可执行。普通管理员仍可在授权数据范围内管理成员。
- HTTP 请求日志仅记录元数据，不记录密码、令牌、请求正文或文件内容。
- 使用独立后端镜像时，也必须挂载它的 `data_dir`，并让前端代理指向该后端。
