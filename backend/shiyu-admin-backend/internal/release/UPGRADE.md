# 升级与回退

## 从 0.2 升级到 0.3 开发版

先在独立测试环境验证对应提交，不要将开发版直接替换生产版本。停写后，按本文方法备份数据库、应用数据目录、密钥和自定义存储目录；保存当前镜像 digest 和配置。

启动单个新版实例时，数据库按顺序从 schema 1 升级到 schema 3。schema 2 新增事项、审批记录、附件关联、通知和设置审计表，以及 Logo、时区和上传上限；schema 3 增加回收站保留期、文件用途及清理状态、重新提交来源。保留原有账号、角色、自定义菜单、设置、文件和审批记录。首次新增的上传上限默认 2048 MiB，保留期默认 30 天。旧版文件按普通文件保留，不自动关联审批或推断为未使用附件。

已使用 schema 2 的 0.3 开发版也需要升级前备份。schema 3 不会自动清理任何文件；管理员须先将未使用文件移入回收站，超过保留期后再选择永久清理。已关联审批的附件不能清理。源码构建最低需要 Go 1.24。

验收时使用两个普通账号完成提交、通知、附件下载、通过/驳回，再验证撤回、修改重提、搜索筛选、附件复用/回收/恢复、重复处理冲突及无关账号无法查看事项。确认系统设置和回收站保留期正确；永久清理仅在可丢弃的测试文件上验收。系统设置仅超级管理员可修改；工作模块对启用账号开放，数据按参与人隔离。

回退须恢复升级前的数据库与应用目录，并使用当时保存的镜像和配置。0.2 和 schema 2 开发版镜像会拒绝 schema 3 数据库；禁止只删除迁移版本记录来强行回退。运行中直接复制 SQLite 主文件可能丢失 WAL 数据，应停写并使用 SQLite backup 或 VACUUM INTO 生成一致性数据库快照，同时保存上传文件和密钥。

## 从 0.1 / 旧提交升级到 0.2

1. 记录当前镜像的不可变 SHA 标签或 digest、Compose 文件和外部配置。不要只记录 latest。
2. 安排维护时间，停止应用写入。备份数据库、应用数据目录和所有自定义文件存储目录。
3. 旧版默认上传目录在容器 /app/data/uploads 内，通常未挂载卷。必须在删除旧容器前复制 /app/data 到宿主机，保留隐藏文件和目录结构。否则重建后无法恢复上传文件。
4. 使用新版 Compose 的 shiyu-app-data 卷挂载 /app/data，将旧 /app/data 内容恢复到此卷。SQLite 的 /data 数据库卷必须同时保留。自定义存储路径需额外挂载原路径。
5. 外部配置中的默认 jwt.secret 改为空，由应用生成 /app/data/jwt.key；也可设置独立的 SHIYU_JWT_SECRET。新密钥应与应用数据一同备份。不要沿用公开示例密钥。
6. 拉取经过验证的固定版本镜像，先启动一个应用实例。启动时执行前向迁移，只有完成后才写入 sys_schema_migrations。禁止多个实例同时进行首次迁移。
7. 检查 /api/v1/system/health、版本页面和日志；验证登录、成员权限、文件下载及上传。旧数据会保留，不会重建默认账号或覆盖已定制菜单。
8. 已知默认密码的超级管理员只能查看个人信息、修改密码和退出；完成改密后重新登录。普通默认账号被停用，由管理员重置强密码后启用。

## 回退

- 本版本不提供破坏性的自动 down 迁移。回退应停止应用，恢复升级前同一时间点的数据库、文件和配置，再启动对应的旧镜像。
- 不要用旧镜像直接连接已经升级的数据库。升级后的新写入需另行导出或接受回退时丢弃；提前安排维护窗口。
- MySQL 的 DDL 不支持完整事务回滚。迁移失败时保持应用停止，检查错误并重试可重入迁移，或恢复备份。
- 备份完成不等于可以恢复。请在独立目录或测试环境演练恢复后再执行正式升级。

## 新安装

启动后访问 /setup；使用 docker compose exec shiyu-app cat /app/data/setup-token 读取安装授权码，填写系统名称及管理员账号、12–72 字节密码。非默认 Compose 部署请加相应 -f 参数。本地开发在配置的 data_dir 下读取 setup-token。

数据库连接通过部署配置管理，安装页会检查数据库连接和文件目录可写性。系统已安装后拒绝重复初始化。
